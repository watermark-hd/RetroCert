# RetroCert

古いMac（証明書ストアが陳腐化しHTTPS接続に失敗する機種）向けの
ルート証明書レスキューツールです。

*(English version: [README.md](README.md))*

## 全体イメージ

    古いMac
      ↓
    RetroCert 起動
      ↓
    VPSから最新CA一覧を取得
      ↓
    Keychainへ反映
      ↓
    HTTPS接続を再試行

VPS側は証明書セットとバージョン情報を静的に置いておくだけなので、
毎回証明書を生成するわけではなく、負荷は非常に軽い設計です。
対象は「証明書更新だけで直るサイト」です。

不特定多数の古い機種ユーザーに使ってもらうことを想定しており、
クライアント本体（実行ファイル一式）自体もVPSから配布します。

## 適用範囲に関する重要な注意（実機検証で確認済み）
RetroCertが直せるのは「証明書の失効・不足だけが原因で接続できないサイト」に限られます。
実機PowerMac G4のSafariで検証した結果:
- 証明書を直し、かつサーバー側も古いクライアント向けにTLS1.0まで許容する設定に
  なっているサイト（このプロジェクトのVPS等）→ **接続できた**
- 世間一般の最新サイト（Apple.com等、TLS1.2/1.3・ECDHE専用構成）→
  **「セキュリティで保護された接続を確立できませんでした」で失敗**
  （証明書ではなくTLSプロトコル/暗号スイート自体の不一致。Tigerの
  SecureTransport実装の限界であり、RetroCertでは解決できない）

つまりRetroCertは「あらゆるHTTPSサイトを直す」ものではなく、証明書問題だけが
原因で、かつサーバー側も古いクライアントに対応しているサイトに限って効果があります。

さらに、Tigerコミュニティの実態としてはSafari/MailはすでにAquafox(TenFourFox系)/
Thunderbirdに乗り換えられている（両者ともFirefox/Mozilla系で、OSのKeychainに
依存しない自前のNSS証明書ストアを持ち、実際にISRG Root X1等の最新ルート証明書を
最初から内蔵していることを実機のバイナリから確認済み）。そのためRetroCertが
直接助けられるのは、あえて標準のSafari/Mail.appを使い続けている少数派に限られる。
「これを入れれば古いMacで今のWebが一通り見られるようになる」という汎用ツールには
ならない、という点を発表時にはっきり明記すること（過大な期待を持たせないため）。

## 他プロジェクトへの転用アイデア
上記の理由で「古いMacのWebブラウジングを直す」という直接的な価値は限定的だが、
実装した仕組み自体は他の用途に転用できる可能性がある。

1. **汎用の「秘密鍵オフライン・HTTP配信でも改竄検知可能」な配布フレームワークとして**
   証明書に限らず、どんなファイル配布にも使えるパターン。
   - `publisher/generate_keys.py`で鍵ペア生成 → 好きなペイロード（ゲームパッチ、
     フォント、設定ファイル、辞書データ等）を`manifest.json`的な形でまとめて署名 →
     `client/verify.py`と同じ仕組みで検証。
   - 「秘密鍵を持つ発行者用マシン」と「署名済みファイルを置くだけの信頼しない
     配信サーバー」を分離するという設計自体が、個人開発の小規模な自動更新機能
     （Sparkle/TUFのような大掛かりな仕組みを導入したくない場合）に転用できる。

2. **`client/verify.py`（外部ライブラリ不要のPure Python RSA署名検証）単体としての再利用**
   `hashlib`と`pow()`と自前の最小限ASN.1 DERパーサーだけで、RSA-PKCS#1 v1.5 +
   SHA-256の署名検証が完結する（約90行）。`cryptography`/`pyOpenSSL`が入れられない
   環境（古いPython、pipが使えないサンドボックス、依存関係を増やしたくない
   インストーラーのブートストラップ処理など）で単独のユーティリティとして
   使い勝手が良い。

3. **対象をMac以外の「証明書が凍結された古い/組み込み機器」全般に広げる**
   `client/store.py`のOS別ディスパッチ層は、まさにこの汎用化のために用意した
   もの。古いルーター・NAS・複合機・産業機器・古いLinux/Windowsサーバーなど、
   ブラウザ以外でHTTPS通信するがOS/ファームウェアの証明書ストアが更新されない
   デバイスは多い。「古いMacでWebを見る」ではなく「証明書が原因で通信できなく
   なったレガシー機器のTLSクライアントを延命するツールキット」として再定義すると、
   Safari/Mail限定よりも広い需要がありそうである。実装するには`store_windows.py`
   や`store_linux.py`のような新しいバックエンドを追加するだけで済む設計にしてある。

4. **(将来的な拡張案、今回は見送り) Aquafox/Thunderbirdの独自NSS証明書ストアへの対応**
   `certutil`が使えないため今回は自動化を見送ったが、`libnss3.dylib`をctypes経由で
   直接呼ぶ独自バインディングを書けば、Aquafox/Thunderbirdの`cert9.db`にも
   証明書を追加できる可能性がある。実現すれば実際に使われているブラウザ/メーラーを
   直接サポートできるため、皮肉だが「本来欲しかった機能」はここにある。ただし
   NSSの内部API・ABIに正確に合わせる必要があり、相応の開発コストがかかる。

## 対応OS
- macOS: OS X 10.4 (Tiger) 以降
- Windows: 対応予定（`client/store_windows.py` を追加する形で拡張する設計、未実装）

## セキュリティモデル（HTTPでも改竄を検知する仕組み）
古い機種はTLSスタックが古すぎてHTTPS自体が使えないことがあるため、
証明書更新の取得はHTTP/HTTPSどちらにも対応しています。
その代わりHTTPは改竄・なりすましされうるため、以下の仕組みで安全性を確保します。

    開発用Mac（秘密鍵はここだけに存在。VPSには一切置かない）
      ↓ 秘密鍵で manifest.json / クライアント配布物に署名
    署名済みファイル (manifest.json + .sig + certs/ + retrocert-client.tar.gz + .sig)
      ↓ アップロード（署名済みファイルのみ。秘密鍵は含めない）
    VPS（署名済みファイルを置いて配信するだけ。秘密鍵は一切持たない）
      ↓ HTTP/HTTPS
    RetroCert（同梱の公開鍵で署名を検証してから内容を信用する）

**重要**: 鍵ペアの生成・署名は `publisher/`（VPSではなく開発用Macなど
信頼できる端末）でのみ行います。VPSに秘密鍵を置かないことがこの設計の核心で、
**VPSが突破されても攻撃者は正しい署名を作れない**ため、悪意あるmanifest.jsonや
証明書に差し替えられてもRetroCert側で検証エラーとして拒否できます。

1. 開発用Macで鍵ペアを生成（`publisher/generate_keys.py`、初回のみ。秘密鍵はこの端末の外に出さない）
2. 開発用Macで `manifest.json` とクライアント配布アーカイブに秘密鍵で署名
3. 署名済みファイルだけをVPSへアップロード（`keys/`はアップロードしない）
4. クライアントは同梱された公開鍵（`client/vps_public_key.pem`）で署名を検証してから内容を信用する
5. 個々の証明書ファイルは検証済みマニフェスト内のsha256で照合するため、
   マニフェスト1つの署名検証で全体の改竄検知が効く

**運用上の注意（Trust On First Use）**: クライアント本体（`vps_public_key.pem`を含む
配布アーカイブ）を最初に入手する際は、現行の安全な環境（HTTPSが使えるPC等）で
入手・署名検証してから古い機種へ転送してください。この最初の入手だけが
信頼の起点になります。以後の証明書更新はHTTP経由でも署名検証で保護されます。

## ディレクトリ構成

    RetroCert/
    ├── client/   … レスキュー本体（Python 3.12想定・配布物そのもの）
    │   ├── retrocert.py       … エントリーポイント（OS共通ロジック）
    │   ├── store.py           … OS別ストア操作のディスパッチ層
    │   ├── store_macos.py     … macOS実装（security/opensslコマンド利用）
    │   ├── store_windows.py   … Windows実装（今後追加予定）
    │   ├── manifest.py        … VPSからのマニフェスト・証明書取得
    │   ├── verify.py          … 署名検証（改竄チェック）
    │   ├── state.py           … RetroCertが追加した証明書のローカル管理
    │   ├── config.py          … VPS_BASE_URL等の設定
    │   └── vps_public_key.pem … 署名検証用公開鍵（配布前に実際の鍵へ差し替える）
    └── publisher/   … 発行者側スクリプト（VPSではなく開発用Macで実行する）
        ├── generate_keys.py   … 署名鍵ペア生成（初回のみ。秘密鍵はこの端末限定）
        ├── build_bundle.py    … 証明書バンドル+署名済みマニフェスト生成
        ├── package_client.py … クライアント配布アーカイブ生成+署名
        └── README.md

## クライアントの使い方（古いMac側、例: PowerMac G4）

    cd client
    python3.12 retrocert.py            # ドライラン（差分確認のみ、変更なし）
    python3.12 retrocert.py --apply    # 実際にKeychainへ反映
    python3.12 retrocert.py --apply --system  # システム全体へ反映（要sudo）

事前に `client/config.py` の `VPS_BASE_URL` を自分のVPSのURLに設定し、
`client/vps_public_key.pem` に実際の公開鍵を配置してください。

## 発行者側の使い方（開発用Mac側、VPSでは実行しない）
`publisher/README.md` を参照してください。
